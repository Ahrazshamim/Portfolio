Case study · Internal tool · Fleet operations

Mass FOTA Automation Dashboard

Shipping firmware to one device is engineering. Shipping it to a fleet, repeatedly, without an engineer in the room, is product. This dashboard turned firmware rollout from a specialist task into a CSV upload and a button.

My role
Product owner + builder
Company
Vecmocon Technologies
Users
Operations & support — not engineers
Input
CSV of device IDs + firmware binary

The problem

Firmware-over-the-air updates existed. That wasn't the issue. The issue was that running one meant an engineer, a terminal, a list of device IDs, and a lot of patience — device by device, checking status by hand, retrying the ones that dropped mid-transfer because the vehicle was in a basement or switched off.

That workflow has three compounding costs, and only the first one is obvious:

  • Engineering toil. Senior engineering time spent on repetitive dispatch instead of building.
  • Release drag. Because rollouts were painful, they got batched and deferred. Fixes that were ready sat waiting for someone to have a free afternoon — which meant the field ran older firmware than it needed to.
  • Error rate. Manual device targeting means typos, missed units, and a fleet that silently ends up on three different firmware versions. Then a support ticket arrives and nobody's sure what's actually running on that vehicle.
The framing that got it prioritised

Internal tools lose roadmap arguments to customer-facing features by default. The argument that worked was reframing it as a release-velocity problem rather than a convenience one: every hour of rollout friction is an hour of delay on every fix behind it. The tool wasn't competing with features — it was competing with the cost of shipping them slowly.

What I built

A dashboard where an operator does exactly two things: upload a CSV of device IDs, attach the firmware build, start the campaign. Everything after that is orchestration.

Before → after: the rollout workflow

CSV-driven targeting

CSV was a deliberate choice over building a query builder or a device-picker UI. Ops already lives in spreadsheets — the device list for "all TATA units in the Pune pilot" already exists as a spreadsheet column, produced by whatever tool they used to get it. Meeting them in the format they already have removed a whole class of "how do I select the right devices" problems, and it meant zero training. The fastest interface is often the one the user has already built themselves.

Campaign orchestration

The backend takes the target list and manages the rollout as a campaign rather than a series of independent pushes: distributing the firmware, tracking which devices have acknowledged, which are in progress, which completed, and which failed. Devices that are offline — parked, powered down, out of coverage — are simply devices the campaign hasn't reached yet, not errors requiring a human decision.

Per-device status tracking

The status view is what turns the tool from a script into a product. At any moment an operator can answer "what version is this fleet on, and which specific units haven't taken the update?" without asking engineering. That single question was previously the source of a large share of internal back-and-forth — and it's also the question that support needs answered before they can diagnose anything.

Product decisions

DecisionReasoning
Self-serve for ops, not a request queue to engineering A tool engineers run on request is still a bottleneck with a nicer interface. Removing engineering from the loop entirely is the whole value; anything less just relocates the queue.
CSV input over a device-query UI Ops already produces these lists. Building a query builder would have been more work, later, and would have needed training — to replace a workflow they were already fluent in.
Campaign as a first-class object Fleet rollouts are inherently long-running and partially complete. Modelling that explicitly, instead of as "a batch of pushes," is what makes offline devices a normal state rather than a failure to triage.
Visible per-device status Answers the version question without a human relay. Turns firmware state from tribal knowledge into something support can look up.

Outcome

  • Rollouts moved from engineering to operations — self-serve, no ticket, no specialist required.
  • Fleet-wide updates became routine instead of an event to schedule around, so fixes reach the field when they're ready rather than when someone's free.
  • Manual targeting errors eliminated; fleet firmware state became consistent and, more importantly, knowable.
  • Engineering toil removed from the release path entirely.

What I'd take to the next one

The highest-leverage product work is often the least glamorous: find the workflow where a specialist is acting as a human API, and remove them from the loop. It never wins a roadmap argument on its own merits, so it has to be framed in terms of what it unblocks. And when you build for internal users, build for the format they already work in — adoption problems are mostly format problems in disguise.
