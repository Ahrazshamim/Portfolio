Flagship case study · Product + firmware

Connected Vehicle Security
& Control Platform

Keyless BLE control, three-tier power management, motion-aware anti-theft, CAN battery interlocks and network-independent recovery come together as one integrated system, shipped on an EC200U tracker. Every feature here constrains every other, which is exactly why they had to be designed as a platform rather than a backlog.

Why these are one project, not five

On paper this looks like a feature list: an app, a power saver, an alarm, a battery check, a locator. In practice they're a single system, because each one's requirements are written in the others' constraints:

  • Anti-theft has to work on a parked vehicle, so it has to survive whatever power saving does.
  • Power saving switches off the mobile radio, so ignition permission, which depends on a CAN battery heartbeat, can't be granted while asleep.
  • The buzzer is wired to the ignition circuit, so making a lock beep means briefly driving the ignition line, which must not read as an ignition-on event.
  • If the mobile network is the only way to find a stolen vehicle, then power saving defeats recovery, which is why the locator had to be radio-independent.

Building these as separate tickets would have produced a device that saves power beautifully and can't protect itself. The architectural commitment that made it work is one sentence: Bluetooth and the motion sensor never switch off. Everything else is negotiable.

System architecture

The tracker runs on the auxiliary battery and never sleeps. The main battery is separate and identifies itself over CAN.

1 · Power modes: saving current without disarming the vehicle

A parked scooter can sit for weeks. A device that stays fully connected drains an auxiliary battery; a device that properly sleeps stops protecting anything and takes seconds to boot when you need it. Neither is acceptable, so the system uses three tiers that shed radios rather than shedding awareness.

Power state machine

Power draw drops roughly 4× in Low Power. Bluetooth, motion sensing and anti-theft stay live in every mode.

The decision underneath all three modes

The device never actually sleeps. It sheds radios instead. That costs a little standby current versus a true sleep state, and buys two things I wasn't willing to trade: zero boot delay on recovery, and anti-theft that's live in Low Power. A security device that has to wake up before it can protect you isn't a security device.

What the user actually notices

  • The app always connects, in every mode. This was the non-negotiable UX requirement: a user must never be told "your vehicle is asleep."
  • In Derated/Low Power the vehicle stops appearing online and live location goes stale. That's a visible, explainable trade, not a fault.
  • Any app command returns it to Active. Rejoining the network takes 20 to 40 s, so the first cloud update after waking isn't instant. We surfaced this in the app rather than hiding it behind a spinner.

2 · BLE keyless control: every refusal is visible

The app locks, unlocks, opens the boot and controls ignition over an authenticated Bluetooth Low Energy channel, with no physical key. Pairing and bonding plus characteristic-level command security prevent replay and unauthorised unlock, and the design spans two radio generations (BLE 4.2 on v1.x, BLE 5.3 with Coded PHY on vB.x, roughly 4× range).

Every command returns an acknowledgement: ACK or NAK with a reason. That was a product requirement, not a protocol nicety. A keyless system that silently ignores you is worse than one that refuses you, because the user's next move is to press it again, then assume the vehicle is broken. Naming the reason turns a support ticket into a UI string.

A hardware quirk that became a spec clause

The buzzer is powered from the ignition circuit, so producing a lock/unlock beep means briefly raising the ignition line. That is emphatically not an ignition-on event. The vehicle stays logically off. Writing that distinction into the spec explicitly is what stopped it being "discovered" later as a safety bug by someone reading the telemetry.

3 · Main-battery detection: asymmetric on purpose

The main battery announces itself with a repeating CAN heartbeat, and ignition permission depends on it. The detection logic is deliberately lopsided: quick to trust, slow to distrust.

Battery presence & ignition interlock

The asymmetry is the whole design. A symmetric threshold would either be so twitchy that ordinary CAN jitter reads as a removed battery, or so slow that a genuinely removed battery leaves the ignition relay live. Splitting it into two timers, one for power logic and a longer one for ignition, so each side of the system can be as cautious as its consequences warrant.

4 · Anti-theft: three detectors, one alarm

Armed by Lock, disarmed by Unlock, and fully automatic in between. It runs in every power mode, including Low Power, which is the requirement everything else was designed around.

Detection & alarm loop

Why three detectors instead of one good one

Redundancy across independent channels, not sensitivity. The wheel sensor and the motion sensor are separate hardware paths, so detection keeps working even if the motion sensor fails. A single-sensor design has a single point of failure that is silent: the alarm simply never fires, and nobody discovers it until after a theft.

The threshold is a product decision, not a constant

Each detector has a debounce so a one-off bump or a passing truck doesn't raise an alarm. Where that debounce sits is the single most consequential number in the system, and the two failure modes are not symmetric:

Tuned…Failure modeConsequence
Too sensitiveFalse alarms from wind, neighbours, traffic The user disables the feature, and it then protects nothing. Terminal.
Too conservativeA careful thief stays under the bar Fails in the case it exists for, but degrades to GPS recovery. Bad, recoverable.

Because the failure modes are asymmetric, I specified a deliberate bias toward fewer false alarms, and tuned against real parked-vehicle data rather than bench shakes, because bench conditions contain none of the noise that causes the problem. The 10-second alarm cycle exists for the same reason: it re-evaluates rather than latching, so a false trigger costs ten seconds of noise instead of a screaming vehicle in a car park.

5 · Reset safety: what survives a power cut

Vehicles lose power. The question is what the device believes when it comes back, and the answer differs per item because the risk differs per item.

StateSurvives reset?Why
Locked / unlockedYes, restored from NV memoryA reset must never silently unlock a parked vehicle. Anti-theft re-arms automatically.
Ignition on/offNo, always offSafety. A relay must only energise on a fresh, deliberate command, never on a boot sequence.
Power modeNo, starts ActiveSafest default; re-enters Low Power normally within minutes.

So a vehicle locked before a power interruption is still locked and still guarded afterwards, while a rider whose vehicle resets mid-journey must re-send Ignition ON. That asymmetry is intentional: security state is restored, actuator state never is.

6 · Find My: recovery when the network isn't there

Every network-dependent locator has the same hole: the moment a thief puts the vehicle in a basement, removes the main battery, or the SIM loses coverage, it stops reporting. So the tracker continuously broadcasts an Apple Find My (OpenHaystack) beacon over Bluetooth. Any passing iPhone silently relays the sighting to Apple's network, where only the owner can decrypt the position.

Offline recovery path

It coexists with the app rather than replacing it: the device advertises the Find My beacon and keeps its normal VEC-<IMEI> name and connectable services simultaneously, so lock/unlock/ignition still work exactly as before. The Bluetooth address is derived from the device's Find My key, so each vehicle appears as its own distinct tag.

A provisioning requirement I had to escalate

Each unit needs its own unique Find My key. Devices sharing one key are indistinguishable in the network and cannot be located individually, which would quietly turn the whole feature into theatre at fleet scale. This is a manufacturing-line requirement, not a firmware one, so it had to be raised as a cross-team dependency before production rather than discovered in the field.

How the pieces interact

InteractionRule

What I'd take to the next one

Two things. First, on an integrated system, write the interaction rules before the feature specs. The most valuable page in this document is the interaction table, not because it's clever, but because every one of those rows was a real argument that got settled once instead of five times. Second, asymmetric thresholds are usually right. Battery-present versus battery-absent, false alarm versus missed tamper, and lock state versus ignition state: in each case the two errors have different costs, and matching the timing to the cost beats picking one "correct" value.
